## 1. 推荐结论

建设“项目与图纸工作台”，在现有图纸管理系统上增加项目归集、受控资料、变更事项、发放记录、专利台账和全过程记录。

用户日常看到熟悉的目录、文件、待办和进度；系统内部准确记录对象身份、固定版本、审批依据、适用范围与执行结果。

必须同时回答六个问题：

1. 这个项目包含哪些原有图号，每张图纸关联哪些资料和变更？
2. 甲方给过哪些要求，适用于哪里，哪些已确认？
3. 为什么改图、具体改了什么、依据和成果分别是什么？
4. 当前正式的是哪一版原图号，当时批准的文件是什么？
5. 哪些文件发给了谁，对方回复了什么，是否还有未处理要求？
6. 项目结束后，能否还原每一次关键决定及对应的原始材料？

**核心产品承诺：项目可以归集多张原有图号；每次正式改动都有原因、证据、修改明细、固定成果、完整审核记录和明确的项目／图纸影响范围。**

## 3. 三种可选路线

| 路线 | 做法 | 优点 | 局限 | 建议 |
| --- | --- | --- | --- | --- |
| A：目录与附件扩展 | 在图纸外加项目文件夹，资料统一上传，增加操作日志 | 操作直观、改动相对少 | 难以可靠证明批准依据、历史文件组合及改图原因 | 只适合作为临时整理工具 |
| B：项目图纸工作台＋受控文档＋变更闭环 | 原图号主档、项目关联、多图纸归集、资料版本、变更证据、图纸发放、专利台账、生命周期视图 | 兼容老图纸，需求覆盖完整，用户操作简洁 | 需要梳理历史图号与项目映射 | **推荐** |
| C：完整 PLM 平台 | 全面产品配置、复杂审批引擎、多组织、多工厂、ERP/MES 双向集成 | 大规模制造协同能力强 | 范围和维护成本显著增加，目前业务规则不足以支持一次性设计完整 | 作为远期扩展方向 |

推荐按 B 的最终业务边界设计，按可验收的闭环分期落地。项目文件夹只是显示方式，原图号、版本、资料、变更和专利关联才是可追溯的业务记录。

## 4. 从成熟设计中借鉴什么

以下是设计借鉴，不代表引入这些产品，也不构成认证符合性声明。参考资料访问日期为 2026-09-11。

- **信息状态与授权用途分开。** UK BIM Framework 的 CDE 指南区分工作中、共享、发布和归档，适合借鉴到“工作资料、确认依据、生产使用、过程留存”。[官方指南，第 11 页](https://ukbimframework.org/wp-content/uploads/2021/02/Guidance-Part-C_Facilitating-the-common-data-environment-workflow-and-technical-solutions_Edition-1.pdf)
- **发放是一项有对象、有收件人、有记录的业务动作。** Autodesk Docs 的 Transmittals 保存文件清单、发放时属性和收件人操作信息。这里借鉴固定发放清单与收发记录。[官方收发文说明](https://help.autodesk.com/cloudhelp/ENU/Docs-Transmittals/files/View_Transmittal.html)
- **一次变更可以组织多个执行任务。** Windchill 的 Change Notice 将工作授权、任务和责任人组织在一个变更事项中。这里借鉴“一项原因，多项受影响成果”的组织方式。[官方变更通知说明](https://support.ptc.com/help/windchill/r13.1.2.0/en/Windchill_Help_Center/changemanagement/ChgMgmtChangeNoticeInfoPageRef.html)
- **改前对象与改后成果分开保存。** Windchill 的执行流程明确受影响对象、成果对象、附件和检查环节。这里对应改前版本、改后版本、证明材料和验收结论。[官方变更实施说明](https://support.ptc.com/help/windchill/r13.1.2.0/en/Windchill_Help_Center/ccm_oview/CCMOviewChangeImplement.html)
- **保留特定时点的完整组合。** Windchill 的 Baseline 固定一组对象及其特定版本。这里用“发布包”向用户表达，并额外落实实体文件保留。[官方基线说明](https://support.ptc.com/help/windchill/plus/r13.1.2.0/en/Windchill_Help_Center/baselines/BaselineAbout.html)
- **版本要有适用范围。** Windchill 的 effectivity 可以表达日期、批次、序列号等条件。本项目只借鉴“版本与适用对象分开记录”的原则，当前范围限定为计划与图纸采用项，不实现生产批次、排程或序列号管理。[官方生效范围说明](https://support.ptc.com/help/windchill/r13.1.2.0/en/Windchill_Help_Center/changemanagement/ChgMgmtEffectivityTypeDetermine.html)

这些原则经过本项目业务裁剪。下面的模型、界面、权限和阶段安排是针对本项目的设计判断。

## 5. 先统一业务对象

### 5.1 用户能理解的层级

```text
项目：示例项目（实际归属待核对）
├─ 项目资料：技术协议、项目会议纪要、统一规范、验收约定
├─ 原图号：JG9416-160/90-150*410
│  ├─ 图纸原件、PDF 出图、三维模型、零件与 BOM
│  ├─ 图纸版本：V1 → V2（每次改图重新审核）
│  ├─ 相关资料：甲方确认、生产反馈、计算与检查记录
│  ├─ 变更事项：BG-2026-023 安装配合修改
│  │  ├─ 原始要求、依据材料、影响评估
│  │  ├─ 改前／改后文件、逐项修改说明
│  │  ├─ 第 1 轮退回、第 2 轮通过
│  │  └─ 审核结论、检查证据、发放记录
│  └─ 专利关联：相关专利、检测结果、续费与期限提醒
├─ 原图号：JG9417-160/90-150
│  └─ 独立版本、资料、变更和专利关联
└─ 原图号：JG9418-100/60-100
   └─ 独立版本、资料、变更和专利关联
```

上面的三个原图号取自用户提供表格中的规格型号，只用于演示导入老图纸时保留原文；是否与实际 CAD 图号相同仍需导入时核对标题栏和图纸台账。项目分组、图纸内容、变更故事和专利均为方案演示，不是已确认的业务事实。

“图纸组”是显示给用户的业务容器，一个组可以代表一套独立总图和配套零件，也可以先只有一张独立图。直接沿用并演进现有 Drawing 容器，首期不在它外面再套一张重复的图纸组表。

同一张图的 EXB、DWG、PDF，以及工作保存记录，不应被误认为多个独立设计。它们通过文件用途、源文件关系和版本归属于同一份设计内容。

### 5.2 每个对象的职责

| 对象 | 负责什么 | 不能被什么替代 |
| --- | --- | --- |
| 项目 | 项目身份、甲方背景、成员权限、共用资料、图纸集合 | 一个自由输入的项目名称 |
| 图纸主档 | 原有图号、名称、图纸结构、版本和技术状态 | 外部计划号、产品规格文本或磁盘文件夹 |
| 图纸组（可选显示概念） | 一套独立工程设计及其零件、BOM、相关文件；底层仍以原图号主档为准 | 外部计划号或普通资料分类 |
| 资料 | 有来源、有分类、有版本的文件档案 | 无法追踪来历的附件列表 |
| 沟通记录 | 一次会议、邮件、电话、甲方反馈及待处理事项 | 已确认的技术要求 |
| 变更事项 | 组织原因、批准、改动、成果、关联图纸与技术检查证据 | “上传了新版”的操作日志 |
| 发布包／发放单 | 固定批准的文件组合；记录向谁发放哪一份组合 | 当前目录内容或动态下载链接 |
| 业务事件 | 说明业务发生了什么，连接相关记录 | 文件夹树或普通服务器日志 |

### 5.3 关系规则

1. 项目可以关联多张原图号；同一张图纸可关联多个项目，但每个关联记录用途和权限，不能复制出失去来源的“新图”。
2. 老图导入时保留原图号、原文件名、原版本、原目录和来源记录；无法确定项目时进入“待归属”，不编造计划号或新图号。
3. 外部计划号、交货序号、产品名称和规格型号只作为可选来源信息；它们不能覆盖原图号，也不能生成图纸、版本或审批任务。
4. 图纸版本按原图号独立演进。图纸发布新版只影响明确关联的项目和引用，不自动改写其他项目的历史版本。
5. 图纸组只作为用户便于浏览的可选分组；结构、BOM、版本和变更仍以原图号主档为准。
6. 资料有一个主归属，可以关联多个项目、图纸、沟通、变更或专利。一份材料不必重复上传。
7. 目录树表达“放在哪里”；BOM 表达“由什么构成”；变更关系表达“为什么产生”。三个关系独立，不允许拖动资料目录改变零件结构。
8. 项目资料夹允许少量自定义目录；资料目录、图纸零件结构和专利台账彼此独立，不用目录名称代替业务关系。

### 5.4 编号与身份

- 项目号、图号、变更号、发放号、专利号分别管理，不互相替代。外部计划号仅为来源字段。
- 内部关系使用稳定 UUID。编号更正保留别名和修改记录，不能让历史链接失效。
- 暂定项目号企业内唯一、原图号按现有台账规则唯一；这是设计默认值，导入前以真实图纸台账确认。只规范首尾空格等已确认无含义差异，原始编号始终保留。
- 同一原图号在不同项目出现时，使用项目关联表表达，不复制图纸；有编号冲突时按项目、来源和标题栏人工核对。外部计划号、甲方编号和产品型号另存，不挤占图号。
- 只有单图纸组的计划默认直接展开展示，减少额外点击。

## 6. 资料分层与要求管理

### 6.1 主归属和默认分类

| 层级 | 默认资料 | 示例 |
| --- | --- | --- |
| 项目级 | 合同与技术协议、统一技术规范、项目会议纪要、通用确认、项目验收 | 整个项目的涂装要求 |
| 图纸／项目级 | 图纸专属技术要求、甲方确认、问题反馈、资料交接 | JG9416-160/90-150*410 的油缸接口确认 |
| 图纸组／零件级 | 计算与选型、工艺依据、设计说明、检查材料 | 某支架的强度核算 |
| 变更级 | 申请依据、影响评估、修改说明、成果、批准与验证 | 改孔要求、批复、对比报告、试装照片 |
| 企业标准库（后续） | 跨项目通用规范和模板 | 企业统一工艺标准 |

普通资料夹允许在这些层级下做少量自定义分类，建议最多额外两层。层级、资料类别、业务状态是三个独立维度；不能靠“已批准”文件夹判断是否真的批准。

### 6.2 一份资料的最小记录

日常上传只要求：标题、类别、归属；从项目／图纸／变更页面进入时自动带入归属，标题默认取文件名。系统自动记录上传人、时间、大小、格式和内容指纹。

涉及要求或证明时，再补充：来源单位／联系人、沟通渠道、发生时间、摘要、关联事项、确认状态、负责处理的人与期限。不是每份照片都要填完整审批表。

支持 PDF、图片、Office 文档、邮件原件、音视频和压缩包保存。各格式的在线预览能力单独评估；不能预览时显示下载和原件信息，不能假装已经识别内容。压缩包内关键证明建议单独提取登记，原包仍保留。

### 6.3 沟通、要求和证明的关系

一次沟通可以产生多条需要执行的要求，每条有自己的编号和闭环：

```text
沟通记录 GT-031（甲方邮件＋附件）
├─ 要求 YQ-051：孔距调整 → 关联变更 BG-023 → 已验证
└─ 要求 YQ-052：图纸标注方式 → 技术待办 → 待甲方确认
```

一般沟通只登记摘要与附件；点“转为待处理要求”或“发起变更”时，系统建立正式事项，自动继承来源材料。

每条正式要求区分：待澄清、待确认、已确认、已落实、已撤回。确认记录包含确认人身份、确认方式、证据、适用项目／图纸和版本；内部录入人不能凭一次上传就把它标记为“甲方已批准”。

口头要求允许先建记录，显示“口头记录／待书面确认”，保留记录人和实际发生时间。是否能先执行，由授权人员按变更风险和紧急规则决定。

### 6.4 同一份资料如何在多个地方出现

- 在图纸页显示“本图纸资料”和“关联项目资料”，清楚标注原始位置。
- 关联可以处于“参考最新资料”或“已采用固定版本”两种语义。正式要求、审批依据、图纸发布包和档案必须固定具体版本。
- 项目规范更新后，已引用旧版的图纸进入影响检查清单；不能悄悄改写旧图纸的依据。
- 移动资料分类不改变资料身份和历史。改变主归属属于显式业务操作，要检查权限和历史引用。
- 关联关系不自动授予源文件访问权。需要对外或跨权限范围使用时，由资料责任人发布明确可见的副本／发放包并保留来源。

### 6.5 同名文件、新版本和矛盾要求

- 拖入同名文件时展示“作为这份资料的新版本”与“建立另一份资料”的区别，不直接覆盖。
- 内容完全相同可提示重复；相同二进制不代表相同来源，同一文件经不同渠道收到时仍可保留独立接收记录。
- 甲方重新发来的邮件是新一次沟通；对同一技术协议的正式修订才是协议的新版本。
- 项目级要求与图纸专属要求冲突时，显示冲突及待决事项。不能仅凭层级、时间更新或上传人身份自动判定优先级。
- 经批准的图纸例外应有适用范围、有效期和审批依据；它不改写项目通用规范的原文。

## 7. 专利台账、检测与期限提醒

专利不是一张普通附件，也不能只靠文件夹记忆。系统建立独立的专利主档，再把专利与项目、原图号、零件、变更和资料建立关联。这样既能看到某张图涉及哪些专利，也能在专利需要缴费或即将到期时提前提醒。

### 7.1 专利主档

每条专利至少保存：专利号／申请号、专利类型（发明、实用新型、外观设计或其他配置项）、名称、申请人、权利人、发明人、所属国家／地区、申请日、授权公告日、当前法律状态、有效期起止、下一次年费截止日、宽限／补缴截止日（有则填）、代理机构／联系人、维护责任人、原始证书和官方通知文件。原始日期和系统登记日期分开保存，人工补录要标明来源。

专利可以主归属项目、企业专利库或某张原图号，也可以被多个项目和图纸引用。专利文件的每个版本都保留内容指纹；变更、甲方要求、检索报告和缴费凭证通过固定版本关联，不能只存一个会变化的链接。

### 7.2 专利检测功能

检测分成三层，结果必须标明证据和可信程度：

1. **台账完整性检测：** 检查专利号格式、重复记录、日期缺失、权利人冲突、有效期早于申请日、下一次年费日期缺失或已过期。
2. **图纸关联检测：** 对图号、标题栏、BOM、技术说明和变更说明做关键词、型号、结构特征和历史关联比对，提示可能涉及的专利和未建立关联的图纸。自动结果只是候选，不自动认定侵权或拥有权利。
3. **外部公开检索（后续可选）：** 在有合规数据源和授权的前提下，保存检索日期、来源、检索式、命中专利和原始结果快照。没有可靠接口时支持人工录入和上传检索报告，不伪造“已完成官方检索”。

变更提交时自动检查受影响原图号的专利关联：若结构、关键尺寸、功能或材料发生变化，提示重新评估相关专利；检测结果必须进入变更审核材料。检测不通过时默认产生“专利评估待办”，不由管理员直接放行；是否阻止图纸发布由企业配置的专利风险规则决定，并保留决定人、理由和依据。

### 7.3 缴费与到期提醒

提醒日期按专利国家／地区、类型和企业规则配置，不把某个固定年限写死在程序里。默认提供可调整的提前 180 天、90 天、30 天提醒，以及到期日提醒和宽限／补缴截止提醒；每次提醒记录发送对象、时间、状态和重试结果。

提醒对象包括专利维护责任人、项目管理权限人员和指定代理机构联系人。责任人变更、缴费完成、官方状态变化或日期更正会重新计算后续提醒，但不会删除已经发生的提醒记录。到期日已过、状态未知、年费凭证缺失或专利状态与台账不一致时，显示高优先级异常；系统不把“已提醒”当成“已缴费”。

专利看板至少提供：未来 180 天需处理、未来 30 天紧急、已逾期、期限已结束、状态待核验、无图纸关联和无维护责任人。可以按项目、图号、责任人、地区和法律状态筛选，并能从提醒直接打开专利主档、关联图纸及缴费凭证。

### 7.4 专利生命周期

```text
登记 → 信息核验 → 检测／关联 → 维护提醒 → 缴费凭证归档
                         ├─ 状态更新／期限变更
                         └─ 到期、放弃或失效 → 归档（历史引用仍可查看）
```

专利到期或放弃不会删除历史图纸、变更或当时的检测结论；只改变专利当前状态并触发影响评估。专利法律效力、续费是否成功和侵权结论必须以官方文件或专业机构意见为准，系统承担记录、提醒和证据组织职责。

## 8. 一次改图如何形成完整闭环

### 8.1 一张变更事项，内部按需要拆任务

用户看到一张“变更单”。它可以影响多个原图号、零件、工艺文件和项目。后台按原图号或责任人建立执行任务，复用现有单图纸工单能力。

最新审核规则：变更后的成果不得由系统管理员直接审核或“代确认”。每个受影响的原图号都生成新的提交轮次，重新经历修改说明冻结、技术审核、独立复核、必要的甲方确认和正式发布；原版审核结论保持只读。管理员可以处理权限、配置、异常和流程重派，但不能代替审核人签署，也不能通过接口跳过审核节点。

例如生产反馈“安装孔干涉”，需要同步改油缸总图、安装座图和相关工艺文件。登记一张变更单，引用生产反馈原件和甲方确认，分别保存各项成果，共用审核结论。生产是问题来源之一，不因此建立生产排程任务。

对于多个项目共用的资产，记录候选影响项目和最终处理决定。未采用新版本的项目要明确记录“继续使用原版／后续切换／不受影响及理由”。涉及共用资产时，影响检查和必要停用决定必须在技术完成前落实；不能仅因其他项目暂不升级就忽略其风险。

### 8.2 推荐流程与关口

| 阶段 | 需要完成什么 | 系统自动做什么 | 下一阶段的条件 |
| --- | --- | --- | --- |
| 登记 | 问题／要求、来源、影响对象、附件或口头记录 | 编号、记录操作者、关联当前项目与图纸 | 基本信息可读，分派责任人 |
| 评估与批准 | 影响图纸、共用零件、相关项目、技术风险、是否需甲方确认及技术检查 | 查找引用关系及未结束变更 | 修改范围明确，必要确认完成；确定本次是否需要专项验证 |
| 修改 | 在授权目标上编辑，维护修改明细 | 建立工作版本、保留编辑与上传记录 | 必要目标已有成果，编辑会话结束 |
| 提交审核 | 本轮实际修改、逐项结果、依据与检查证据 | 冻结依据、改前／改后版本及本轮快照 | 无缺失原件、无版本冲突、关键材料可查看 |
| 技术审核 | 核对修改正确性、要求覆盖及验证证据 | 记录签署范围和准确快照 | 必须审核人通过；退回进入下一轮 |
| 图纸发布 | 确定项目采用版本，核对配套图纸、BOM 与依据 | 固定图纸发布包，记录替代关系 | 本次范围完整，必要审核与发布前检查通过 |
| 技术完成 | 核对修改项、审核结果、发布引用及本次约定的验证 | 形成技术结论和变更档案 | 必需技术工作完成；如本次明确要求发布后验证，则完成后再结束 |
| 发放与回复（关联流程） | 指定收件人、用途及是否需回复，登记外部回信 | 固定发放单、生成必要待办 | 独立记录发送和回复；普通阅读回执不默认阻止技术完成 |

“技术完成”只表示本次 CAD 改图闭环完成，不声称产品已经生产、安装或交付。一般改图不强制现场试装、旧物料处置或生产确认。若这次变更确有测量、试装等技术验证要求，在评估时明确项目、检查人、证据和关口；已设为必需的检查不能静默跳过。发布前必须完成的验证与发布后允许补充的验证分开标明。

### 8.3 修改明细必须能逐项核对

每条明细记录：目标对象、位置／页码／零件、原内容、新内容、原因、依据版本、成果版本、检查结论。前后值包含单位；图形难以结构化时，至少有人工描述和定位截图。

| 修改项 | 原内容 | 新内容 | 依据 | 验证 |
| --- | --- | --- | --- | --- |
| 示例图 A，总图第 2 页 C3 区 | 安装孔直径 Ø10 mm | Ø12 mm | 甲方确认邮件 GT-031 的固定附件版 | 校核通过 |
| 示例图 B，安装座 B-07 | 孔距 80 mm | 90 mm | 生产问题照片及甲方确认邮件 GT-031 | 第 2 轮尺寸配合校核表 |
| 工艺卡 GY-015，第 3 工序 | 原钻孔要求 | 新钻孔与检验要求 | 上述图纸更改 | 技术审核确认 |

文件上传变化、标题栏属性变化和 BOM 增删改可辅助自动生成差异；CAD 几何差异受格式、转换结果和算法限制，必须显示支持范围与失败原因。自动比较结果不能替代人工确认“本次为什么改、是否满足要求”。

### 8.4 证据分角色保存

- 申请依据：甲方来信、现场问题照片、会议纪要、生产要求。
- 决策依据：影响评估、甲方确认、内部批准、例外授权。
- 修改成果：新 CAD、PDF、BOM、工艺文件和逐项修改说明。
- 检查证据：技术校核记录、检查报告；本次需要时附试装、测量或现场照片。
- 发放证据：固定发放清单、邮件回复、签收单；与技术检查分别归类。

一份材料可以同时支持多个修改项，通过引用建立关系。不要要求用户重复上传，也不要把所有文件混在“其他附件”中。

### 8.5 退回、补件、取消和紧急变更

1. 每次送审形成独立轮次；退回保留原成果、证据、意见和签署，重新提交产生新轮次。
2. 审批必须绑定轮次和内容指纹。审批页面打开后，若成果或依据已变化，旧页面不能批准新内容。
3. 改动审批依据、技术内容、目标范围、采用范围或关键验证结论，需要重新评估相应批准；首期默认重新提交整体包，避免漏审。
4. 审后补充说明作为新的补充记录；若只是补录既有回执，应保留实际发生时间和录入时间，不篡改过去快照。
5. 驳回、撤回、取消各有含义。未发布事项可取消并保留全过程；已发布成果必须通过停用、更正或新版本处理，不能用取消工单抹去既有发放事实。
6. 如企业需要紧急技术处理，可配置简化审批，登记授权人、原因和补齐事项。临时技术例外另外标注范围与到期条件，不从计划号中的“急”自动启动该流程；首期不接管在制品或停工控制。
7. 技术内容变动必须保留复核、固定版本和证据。取消本次必需检查要走有理由的重新评估并留痕，不以管理员身份直接免验收。临时例外到期后显示失效，阻止依据该例外新发布图纸。

### 8.6 变更风险分级

| 类型 | 示例 | 推荐控制 |
| --- | --- | --- |
| 资料整理 | 分类、标签、无技术含义的标题更正 | 有权限即可调整，自动留痕；冻结档案用更正记录 |
| 一般技术变更 | 局部尺寸或工艺修正，影响图纸和项目已核实 | 修改范围确认＋独立技术复核＋相关项目／图纸＋检查证据 |
| 重大变更 | 关键性能、配合关系或跨项目共用设计受影响 | 增加相关技术／质量审核，按实际要求附甲方确认及专项验证 |
| 紧急临时措施 | 现场需临时限制使用或经授权临时处理 | 限定范围、时效和授权人，补审待办及到期控制 |

风险条件通过可理解的配置启用，不首期引入任意可编程审批流程。

## 9. 正式用图：图纸版本、项目引用与发放回执

### 9.1 三种版本与两种记录

| 名称 | 回答的问题 | 例子 |
| --- | --- | --- |
| 文件保存版本 | 某个文件保存过哪些内容？ | 支架.exb 第 17 次保存 |
| 技术发布版本 | 哪一版工程设计经过技术批准？ | 支架图纸组 R2 |
| 项目图纸发布包 | 这个项目正式采用哪一组图纸、BOM 和依据？ | 示例项目／P02 |

保存版本由系统管理，普通用户默认只看工作版与正式版。项目引用记录说明哪个固定包当前有效，发放记录说明哪个固定包发给了谁；它们是业务事实，不另称为文件版本。显示版本号可以延续现有 V1、V2，但不能靠工单完成次数推断文件组合。

### 9.2 发布包里固定什么

项目图纸发布包固定：项目与图纸关联快照、每个原图号的发布版本、每份文件的准确版本、零件修订、BOM 内容与数量单位、已采用要求和资料版本、批准记录及用途。BOM 数量属于技术结构，不是启动表中的生产数量。

应保存显式的清单及关联实体文件；不能只记录“当时这个目录叫什么”。未变动的图纸可沿用原正式版本，不需要为整个项目内所有文件强行增加版号。

CAD 原件、转换结果和 PDF 出图之间记录来源版本及生成信息。转换失败时不能用旧预览冒充新成果。发布策略指定哪些可视成果是审核／现场必需文件；必需成果缺失则阻断发布。

### 9.3 多图纸一起发放的完整性

修改示例图 A 与示例图 B 的配合关系时，必须将它们作为一个发布单元核对。若其中一个仍待审，默认阻止把不完整组合正式发布。

独立且无配套依赖的图纸可以分别完成审核。更新项目包时把已批准改动与未变动的既有正式版组成新清单；仍在修改的工作版不能混入。确需拆分技术发布范围时必须明确兼容性和审核结论，不根据生产批次自动拆分。

相同发布操作重复提交只产生一个包。多人并发发布时检查项目、原图号、文件和审批轮次是否仍然一致；有变化则给出可读冲突，不能以最后保存者覆盖前者。

### 9.4 当前正式版的确定规则

首期每个项目保留一份当前正式图纸清单，初始可以为空。清单固定各原图号的图纸版，历史清单永久可查。一次项目发布在同一事务中生成新清单和替代记录；两个并发发布不能产生两个互相矛盾的当前清单。

新工作版和新的技术发布版都不自动替换所有项目。某项目决定引用新技术版时，检查其依据、配套兼容性和必要审核，再生成该项目的新包。即使只是复用已批准图纸，也要记录本项目引用决定；无需重新证明未改变的设计内容。

查图默认进入“本项目正式版”，另有“工作中”“历史版本”。没有正式包时明确显示“尚未正式发布”；不能自动回退到工作版或全局最新版。历史技术图已发布但项目尚未确认引用时，显示两个不同状态。

开始改图不自动作废现有正式版。明确发现旧版不可用时，由授权人员登记停用范围、原因和关联变更；受影响项目引用显示停用，不能继续从当前正式用图入口取用。历史文件仍保留且带停用标识；不自动切回更旧版本。一张图纸在一个项目停用不抹掉其他项目的历史引用。

首期不提供生产批次选择、按生产启动日期切换、库存／在制品处置或生产调度。图纸正式版的选定和变更始终可追溯。

### 9.5 发放和回执不是一回事

一张发放单记录：发送人、收件组织／岗位／人员、固定包、用途、发送时间、截止时间、通道和回执要求。

发放用途至少区分“沟通／征求确认”和“正式图纸”。前者可以包含明确标注状态的草稿、问题照片或资料，仍固定发送时的准确文件版本；后者只能引用符合本项目正式用图规则的成果。发给甲方征求意见不需要先伪造一次正式批准，也不能让草稿进入正式用图入口。

状态分别保存：

1. 系统已发送／发送失败；
2. 接收人已查看或已下载（可观测时）；
3. 接收人确认收件，或按本次要求回复具体技术问题；
4. 外部反馈由内部人员登记时，保存原件、登记人和实际回复时间。

“已读”不能替代技术批准、甲方同意或生产实施。收件人任务只按被要求的动作完成，不让所有人都填四遍。

甲方首期可以不注册账号：内部人员导出固定文件包，通过原有渠道沟通，随后登记发送凭据与回复原件。导出完成只能记为“已导出”，没有发送证据不能记为“已发送”。记录应写“由某人登记的甲方回复”，不得伪装成甲方本人在系统中签署。门户和邮件集成可后续接入。

### 9.6 旧版和离线文件

- 查图入口优先展示当前项目引用的固定包，并清楚显示项目号、原图号、版本和状态。
- 历史下载入口展示“历史版本”与当前授权状态；PDF 打印件可带发放号、版本、用途和核验码，原 CAD 文件保持原件。
- 已下载或打印的副本无法由系统保证远程收回。系统保存停用告知和回信；有实际回收证明时可以上传，不自动生成生产执行流程。
- 后续桌面离线能力应展示最后核验时间、包版本与适用范围；断网时不冒称已核验为当前有效。
- 撤销发放不能自动删掉文件或过去回执；补发和纠正都产生新记录。

## 10. 状态与生命周期如何避免互相混淆

### 10.1 不用一个状态字段表达所有进度

| 对象 | 核心状态 | 独立显示的信息 |
| --- | --- | --- |
| 项目 | 整理中、使用中、已归档、已取消 | CAD 资料完整性、未结变更、待确认要求、待回复记录 |
| 工程成果 | 工作中、审核中、已发布 | 是否在某项目被引用、是否有停用记录、是否有新版 |
| 变更事项 | 待评估、待批准、修改中、待审核、待发布、技术完成、已取消 | 本次确有要求时另显示待验证；退回是轮次结论并回到修改中 |
| 资料记录 | 已登记、待确认、已确认、已撤回等按类别定义 | 归属、用途、版本、是否被作为正式依据 |
| 发放单 | 准备中、已导出、已发送、待回复、已完成、已撤销 | 每个收件人的发送凭据、查看、收件确认及技术回复 |

发布历史的内容固定，引用有效性可通过后续事件发生变化。某版在项目 A 被替代，不意味着在项目 B 也全局作废。

项目过程展示：资料归集、技术要求确认、图纸审核、改图处理、正式发布、文件发放、专利维护、档案整理。它们可以反复发生或同时进行，不能强制变成单向生产进度条；直接显示“2 张图纸、1 项待审、1 份待回复、1 个专利待缴费”等实际计数，不虚构完成百分比。

### 10.2 生命周期提供三种视图

**对象树：找东西。** 按项目、原图号、资料、变更、专利和发放分类导航。

**业务时间线：看发生了什么。** 自动汇总关键业务事件，按项目、图纸、变更、专利、人员和事件类型筛选。

**变更因果树：看为什么变成今天这样。** 点击某个版本或变更，展开来源要求、证明材料、审批轮次、成果版本、技术检查、专利影响和发放回复。

不默认绘制整个项目的巨大关系网。一个屏幕先显示当前路径，相关分支按需展开；同一材料被多处使用时显示“关联”，不复制为多条来源不同的事实。

### 10.3 一个具体生命周期示例

```text
示例项目（以下事件均为演示）
└─ 原图号 JG9416-160/90-150*410
   ├─ 09-01 技术要求确认
   │  └─ 技术协议 ZL-001 v1、图纸要求 YQ-010
   ├─ 09-03 图纸发布包 P01 发放
   │  ├─ 原图号 V1、对应 BOM 与工艺
   │  └─ 固定清单、发送凭据与收件回复
   ├─ 09-05 甲方反馈安装孔调整
   │  └─ 沟通 GT-031 → 要求 YQ-051 → 变更 BG-023
   │     ├─ 依据：甲方邮件、问题照片
   │     ├─ 第 1 轮：提交 → 退回（支架未同步）
   │     ├─ 第 2 轮：两组图纸与工艺同步 → 技术审核通过
   │     ├─ 项目发布 P02：替代 P01，旧清单保留
   │     ├─ 修改明细、校核证据齐全 → 技术完成
   │     └─ P02 发放 → 收件确认与甲方回复
   ├─ 09-09 专利年费提醒
   │  └─ 专利 CN-XXXX：距缴费节点 30 天，责任人待处理
   └─ 09-10 资料完整性检查及项目归档
      └─ 图纸原件、全部变更轮次与完整档案包
```

日期和编号仅用于方案示例。

点击“第 1 轮退回”，必须打开第 1 轮实际文件与当时意见；点击 P01，必须看到 P01 的完整组合，不受当前 P02 影响。点击专利提醒，必须看到期限来源、提醒记录和缴费凭证状态。

### 10.4 每条事件记录什么

事件包含唯一标识、业务类型、操作者身份快照、所属项目、相关原图号／资料／专利、发生时间、系统登记时间、状态前后值、简明说明、关联版本、审批／发布标识与来源事件。

- 业务事件由后端业务事务产生。不能只由前端提交“我已发布”的文字日志。
- 上传、批准、退回、项目引用、发放、回复、停用、检查、专利提醒、归档是默认可见事件；自动保存等细碎操作折叠进详情。
- 业务事件与审计日志分开：前者方便理解过程，后者供管理人员检查权限和操作。
- 跨多个项目的同一变更只有一个源事件，通过关联出现在各项目；项目汇总去重，不重复计算完成量。
- 同一业务对象的事件使用服务器分配的顺序号，并记录因果与事务标识；不能仅凭可能相同或有偏差的时间戳判断操作先后。
- 外部事件保留“实际发生时间”和“录入时间”，补录必须有标记，不让后来录入伪装成当时系统就已掌握。
- 首期“回看当时”以已冻结的发布包和提交轮次为准确入口。任意时刻全量回放属于后续能力，只对已具备足够记录的时期承诺可还原。
- 历史资料缺失时显示“历史原件缺失／待补录”，保留能证实的内容，不生成虚假的完整历史。

## 11. 页面与日常操作设计

### 11.1 导航建议

保留已有图纸库与零件库，新增或整合为七个主要入口：我的工作、项目与图纸、图纸资产、资料中心、变更中心、专利中心、记录与归档。后台设置另放管理区。

“我的工作”只放分派给自己的待办、需要关注的变更、专利提醒和常用项目。所有全局中心是跨项目查询入口，具体操作仍能在项目／图纸页面原位完成。

### 11.2 项目页面

顶部显示项目号、名称、甲方和 CAD 资料状态。主体显示原图号列表、项目级资料、项目待决问题、专利提醒和关键记录。图纸列表展示版本、未结变更、待确认资料和最近一次正式发放。成员权限放在项目设置，不把生产负责人塞进主页面。

项目资料上传在此默认项目级；任何已授权图纸页也可查看相关项目资料。

### 11.3 图纸页面是主要工作场所

顶部：原图号、项目路径、CAD 资料状态、当前图纸发布包。用户按原图号查图，不需要输入外部计划号、批次或启动时间。生产计划负责人、启动日期和加工安排不出现在 CAD 图纸主页面。

主标签：概览、资料、变更、发放与回复、专利、全过程。

图纸页默认列表或卡片，包含图号、名称、工作状态、最新技术版、项目引用版、关联问题。点击一项进入已有图纸查看、零件结构、BOM 和版本比较工作区。

主要操作：导入老图、上传资料、发起变更、关联专利、发布图纸。导入时保留原图号、原版本和历史文件；不得为了适应计划号而改号或复制文件。页面不同时堆出大量业务按钮。

### 11.4 上传时减少填写

1. 用户在计划或变更中拖入文件。
2. 系统自动带入上下文，并根据来源入口预选类别。
3. 批量文件提供一次统一设置和少量逐项更正。
4. 命名、格式或内容识别只给建议；若属于不同图纸组或存在版本冲突，显示清楚的分组预览。
5. 原文件上传成功与预览转换成功分别显示。上传中断可以续传；分类未完成可放入待整理区。
6. 待整理资料不能成为已确认技术依据，阻断只发生在确实需要其成为正式依据的阶段。

### 11.5 变更详情布局

顶部显示变更编号、标题、状态、处理人和下一步；正文按“要求与依据、影响范围、修改成果、审核记录、检查证据”分组，关联发放记录可直接打开。

对比入口自动选择本轮改前／改后版本；证据可原位预览；右侧详情只在需要时展开，避免用户来回切换许多页面。

审核人首先看到“改了什么、为什么改、影响哪些图纸和项目、是否还有缺项”，然后才是文件明细。查图人员首先看到“这个原图号当前正式版本、发生过什么修改、相关要求和专利提醒在哪里”。

### 11.6 搜索与易用性规则

- 一个搜索框可按项目号、原图号、外部计划号（如有）、文件名、变更号、专利号查询，结果带完整归属路径和版本状态。
- 有权限的文件内容检索和 OCR 作为后续增强；原文件是最终依据，识别错误可纠正并保留来源。
- 保留用户最近位置、筛选和展开状态；单图计划减少一次无意义跳转。
- 空状态明确告诉用户下一步；权限不足与数据不存在按安全规则显示，不返回敏感项目名称。
- 关键限制用原因和解决入口解释，例如“原图号 V2 尚未完成重新审核，暂不能生成正式图纸发布包”。
- 必填项按阶段出现：登记时少填，批准／发布时补齐。常规动作自动形成记录，用户不用再手写时间线。
- 首期优先保证桌面使用和车间便捷查看。移动端先提供查图、回执和拍照反馈，再扩展复杂编辑。

## 12. 权限、责任与通知

### 12.1 默认责任分工

| 角色 | 主要职责 | 默认边界 |
| --- | --- | --- |
| 项目管理权限 | 管理成员、项目归属、图纸集合和归档 | 是授权角色，不是生产计划负责人字段；不能覆盖已批准的成果与签署 |
| 图纸发布权限 | 核对项目引用组合、发布与停用 | 不替代独立技术审核；可以由有授权的技术人员兼任 |
| 设计／技术人员 | 编辑、提交成果、解释差异 | 不批准自己编制的生产技术成果 |
| 审核／质量人员 | 技术检查、验证结论、关键放行 | 只签署自己获授权的范围 |
| 文件接收人／问题反馈人 | 接收图纸、回复要求、上传问题照片与说明 | 可以来自生产或甲方；不因此成为 CAD 计划负责人 |
| 资料管理员 | 分类、归属、来源登记、归档检查 | 资料整理权限不等于技术批准权限 |
| 系统管理员 | 账号、配置、运行和恢复 | 不默认取得代替甲方确认或任意修改审计的业务授权 |
| 外部人员（后续） | 查看明确发放内容、反馈和签收 | 只见被授权的资料包 |

一人可以兼任多个角色，但每次操作记录真实身份与当时角色。重要生产成果默认编制人与复核人不同；人员不足时可以指定另一名有授权人员，不以隐藏自审解决。

### 12.2 权限计算

项目成员权限为基础，图纸、资料和专利可进一步收紧，敏感资料可单独限制。权限检查覆盖列表、搜索摘要、预览、下载、批量导出、历史版本和关联对象。

把受限文件关联进一个公开项目不能自动扩大可见范围；打包时逐项校验。需要让特定人员只看某个冻结图纸发布包时，使用明确的发放授权，不授予整个资料库权限。

人员离职后保留历史签署姓名与身份快照，未完任务转交并记录交接；不得让接任者的姓名替换历史操作者。

### 12.3 通知要形成待办闭环

通知分为“需要你处理”“需要你确认”“仅供知晓”。前两类对应持久化任务，不能仅靠一个红点。

触发条件包括分派、退回、待审、关键依据更新、发放、未按期确认、临时措施到期和图纸发布包撤销。普通编辑与批量上传合并提醒，避免刷屏。

消息直接打开对应轮次／发放单；完成任务后其他设备同步状态。失败发送可重试并去重，但不撤回已经成功的业务发布。外部渠道首期采用人工登记方式也必须保留闭环。

通知模板包含：对象、发生了什么、需要做什么、处理人及已设置的办理期限；这里的期限属于审核／回复任务，不是生产启动日期。敏感资料名称不向无权限收件人泄露。

## 13. 档案与长期可靠性

### 13.1 档案包内容

项目档案包含项目下所有原图号、资料、变更、发放和专利记录。每份档案包括：

- 目录、项目／图纸信息、成员与责任记录；
- 收到的要求、沟通记录及原始资料；
- 每个正式发布包及其原始文件、必要出图、零件和 BOM 快照；
- 每次变更的依据、修改明细、所有提交轮次、审核意见及结论；
- 发放清单、发送凭据、技术回复、签收记录，以及本次确有要求的检查／验证证据；
- 未决问题、经批准的例外、补录说明；
- 文件清单、大小、版本、内容指纹和关联索引，及生成时间、导出范围。

建议导出 ZIP 原件包＋可离线打开的目录／过程报告＋机器可读清单。PDF 汇总报告可在后续报表阶段实现，不能只导出 PDF 而遗漏原 CAD 和原始证据。

技术完成不会自动把项目归档。归档前检查项目归属、应归档的图纸与资料、所有变更结论、专利台账状态、必需技术确认和文件完整性；未结束的必需事项须解决。一般回执确需留待后补时，要有明确例外说明及办理记录，并在档案目录显示缺项，不能标成全部齐全。项目归档固定原图号档案的准确版本，后续补充生成新档案版本。已归档项目需要继续改图时，由有权限人员显式重新开启并留痕，原档案保持只读。

### 13.2 保留规则

正式成果、来源原件、被任一送审轮次引用的文件、被批准依据引用的资料、已发放文件、回执和验证证据必须受保护。退回、取消或未被最终采用不自动取消其留存价值。

普通自动保存的临时版本可以依保留策略清理，但必须确认不存在任何受保护业务引用。清理检查覆盖提交轮次、变更依据、发布包、收发文、档案、零件修订和转换来源，不能只看“是否正式版”。

归档后更正采用补充记录和新的档案版本。归档与备份独立：归档用于查阅责任与过程，备份用于灾难恢复。

### 13.3 防止“文件存了但记录不可信”

文件内容写入不可覆盖的版本对象，登记大小与 SHA-256；业务批准和快照以追加记录保存；应用账号无权直接更新或删除正式审计记录。高要求部署可增加独立只读副本或对象锁定。

内容指纹只能帮助检查文件是否变化，不能单独证明甲方身份、签名真实性或事实是否正确。需要可靠外部签署时另行接入身份验证与签署服务，保留原始凭据。

### 13.4 运行和恢复

- 数据库与文件存储进行一致性备份，保留备份清单并定期执行恢复演练。
- 建议以“关键业务恢复不超过 4 小时、最多丢失不超过 1 小时已提交数据”作为讨论和演练目标；能否达到需结合部署与预算验证，不能当作当前承诺。
- 监控容量、失败上传、转换失败、通知积压、档案生成失败、备份失败及断开的引用。
- 文件存储不可用时，显示准确状态，不能出现业务成功而文件缺失的假象。
- 长期保存年限与到期处置按企业实际要求配置；首期对正式业务档案默认不自动物理删除。
- 扩大资料格式后同步控制文件大小、配额、实际文件类型、危险文件隔离和预览环境；上传文件不在服务进程中直接执行，存储路径不由用户文件名决定。

## 14. 与现有代码衔接的技术设计

### 14.1 总体架构

继续使用现有 Go、PostgreSQL、Vue 与桌面端基础。采用单体应用内的清晰业务模块；现阶段不需要微服务、图数据库或完整工作流引擎。

新增／扩展领域：project、document、correspondence、change、release、patent、record、notification、archive。继续复用 drawing、attachment、upload、editing、versioning、review、partindex；不新增 plan 主领域。

业务状态变化在服务端事务中完成；查询页面使用适合展示的汇总数据。生命周期树由关系与业务事件构建，数据库仍可使用关系表。

### 14.2 建议数据模型

以下为逻辑模型和主要约束，正式表名及迁移脚本在实施阶段确定。

| 模型 | 关键内容 |
| --- | --- |
| projects／project_members | 项目身份、编号、甲方、CAD 资料状态、成员权限；不增加生产负责人 |
| project_drawings | 项目与原图号 Drawing 的关联、用途／位置、排序；不覆盖原图号，不创建计划明细层 |
| drawing_source_refs（可选） | 外部计划号、交货序号、产品名称、规格型号、来源行号及备注；只用于追溯和检索，不参与 CAD 审批 |
| document_folders | 主归属、父目录、名称、排序；同归属、禁止成环、有限层级 |
| documents／document_revisions | 资料身份与业务元数据；修订记录固定元数据与附件版本 |
| document_links | 资料或其固定修订与相关对象的关系类型、来源、适用目的；主归属与引用分离 |
| communications／communication_files | 渠道、外部联系人、摘要、原件版本、发生时间与登记时间 |
| requirements／requirement_revisions | 正式技术要求、来源、关联项目／图纸、处理人、确认和落实关系；普通资料无需建立要求 |
| change_cases | 跨图纸／跨项目的变更主事项、原因、风险、批准范围、业务状态 |
| change_case_tasks | 主事项与现有 change_requests 的关联；执行任务仍可按原图号管理 |
| change_items／evidence_links | 逐项原／新内容、影响对象、依据与成果的固定版本 |
| change_submissions／approvals | 提交轮次、冻结清单、内容指纹、签署人、决定、意见、模板版本 |
| drawing_releases／release_items | Drawing 正式技术快照、零件修订、结构、BOM、文件与元数据 |
| project_releases／release_items | 项目图纸发布包，固定原图号、图纸发布版、资料与批准清单 |
| project_adoptions／release_status_events | 项目当前引用哪个固定包、替代关系、停用范围及原因；不按生产日期或批次调度 |
| transmittals／recipients／receipts | 固定文件清单、导出、发送凭据、收件人、技术回复、补发与撤销 |
| change_checks／check_evidence | 本次约定的技术检查、是否必需、发布前／后关口、检查人、结论与固定证据；一般变更无需现场任务 |
| patents／patent_events／patent_links | 专利主档、状态与期限、图纸／项目关联、检测结论、提醒、缴费凭证和历史事件 |
| business_events／event_links | 稳定事件、归属、因果、版本和关联关系 |
| outbox／notification_tasks | 事务内待发送事件、可靠重试、用户待办和去重标识 |
| archive_packages／archive_manifests | 冻结档案、内容清单、导出状态、校验与补充版本 |

资料文件沿用同一套上传、二进制存储和附件版本服务，不再复制一套文件引擎。可以让附件新增 `document_id` 主属类型，与原 `drawing_id`／`part_id` 保持“恰好一个主属”的约束；`document_revisions` 固定业务元数据并关联已有 `attachment_version_id`。外层资料描述与底层二进制版本职责明确，复合外键／事务校验防止关联到其他资料的附件版本。

多文件会议材料通过 communication_files 组织；一个“文件夹”不必被强行建成一份多文件文档。CAD 原件与派生成果继续通过现有附件体系扩展来源关系。

主归属使用可验证的外键约束。对象类型较少时优先显式关联表和约束，不用任意字符串 owner_type／owner_id 逃避参照完整性。

### 14.3 关键不变量

1. 同一项目下的原图号按现有图纸台账规则唯一；图号更正不改变内部 Drawing 身份。
2. 一个项目关联多个 Drawing；外部计划号、周启动表行号、产品名称和型号不自动生成图纸身份，生产字段不成为任何 CAD 流程的必填项。
3. 资料夹父子属于同一主归属且不成环；项目、目录与 BOM 结构独立。
4. 任何批准、提交、发放和归档都引用准确版本，禁止通过 current_version_id 动态解析历史。
5. 文件内容一经形成版本不可覆盖；正式快照内容不可原位修改。
6. 文件版本必须属于所声明的附件；发布中的零件修订必须属于所声明零件；图纸发布版必须属于项目发布清单引用的 Drawing。
7. 发布时冻结 BOM 的结构、数量、单位和零件修订，不能只保留一条会变化的 BOM revision 计数。
8. 同一发布事务校验所有对象、审批轮次、技术检查及内容指纹；任何一个不满足就不能发布该组合。
9. 共用文件在并发变更中以真实附件／资产身份检查冲突。锁不能只局限在 drawing_id，否则不同项目可能同时改同一零件。
10. 首期默认同一受控目标串行变更；确需并行则显式分支，重新确认基线并复审后发布，不静默合并二进制文件。
11. 一个项目最多有一份当前正式清单；每个原图号在清单中只有一个准确技术版。停用状态单独保留，不能默认为另一旧版或工作版。
12. 技术完成、项目引用、导出、发送、收件确认是独立事实，不能互相隐式代填，更不能推断生产完成。
13. 被历史业务引用的版本禁止删除或置空；清理作业也必须遵守。
14. 变更后的每个受影响图纸必须有新提交轮次和完整审核记录；管理员不得代签或跳过节点。
15. 专利日期、状态、提醒和缴费凭证均保留历史事件；已提醒不等于已缴费，状态未知不等于有效。
16. 事件、批准和对应业务状态一起提交；消息发送失败不丢失待办，不回写虚假的发送成功。
17. 业务引用不扩大权限；单文件与批量导出执行同样的授权检查。

### 14.4 上传、事务与异步工作

上传采用现有临时会话和对象存储流程：先保存并校验文件，再在业务事务中登记资料／版本引用；失败对象作为未引用临时文件处理。数据库事务不假设能回滚已经写入的文件。

转换、对比、通知、档案打包使用持久化任务和可重试状态。发布前需要的文件必须已经存在并完成要求的检查，发布事务不等待长时间 CAD 转换。

采用事务内 Outbox 保存“待发送消息”。提交成功后异步发送，幂等重试；不需要首期引入独立消息中间件。业务事件立即可见；搜索索引、汇总视图可异步更新并显示刷新状态。

新增模块的修改操作使用现有修订号并发控制与命令幂等机制。确认／发布接口显式提交 submission_id、expected_revision 和幂等键，不通过普通状态 PATCH 绕过流程。

### 14.5 现有能力的具体演进

- Drawing 保留为原图号主档；project 字符串逐步退为历史兼容字段，项目查询改为真实关联表。
- 项目页面包住现有图纸工作区，现有编辑、预览、BOM、零件索引操作继续可达。外部计划号、启动日期、加工安排、负责人和生产进度留在原生产计划系统；本系统只保存可选来源引用。
- 现有 change_requests 成为改图任务。主变更事项增加多图纸统一评估、总体提交／发布和检查证据；每次变更后的每张受影响图纸都必须重新提交并走完整审核，管理员不能代签。已有执行／验收状态需明确映射为技术操作，不能直接套成生产状态。
- 主事项提交冻结每个子任务的准确轮次及共同依据，不只是关联可变化的子任务 ID。初次批准冻结允许修改的目标与基线，追加目标或切换基线必须重新评估，不能在执行中扩大授权。
- 子任务技术审核通过只标记“本项审核通过”。由主事项的发布命令统一校验和发布，不能每通过一个子任务就部分放出配套图纸；管理员的异常处理不产生技术签名。
- 图纸首次正式发布走明确的发布命令；存档不再承担隐式发布职责。已有触发器及历史状态映射需迁移验证。
- 一个项目图纸发布包可以引用已经正式发布的原图号；同一资产不同项目的引用由 project_releases 和 project_adoptions 管理，不随全局指针同步漂移。
- 专利领域新增独立台账、期限事件和提醒任务；检测结果只作为技术风险输入，不能替代专利代理机构或官方结论。
- 附件清理、版本外键和物理清理队列先完成留存规则审查，避免新增记录再次被旧清理流程破坏。
- 零件索引中的 project_id、DrawingID 等历史混合语义需要迁移和兼容，不仅修改页面文案。

## 15. 历史数据迁移与上线

### 15.1 基本原则

采用增量迁移、映射表、备份和校验报告。仓库旧文档曾允许开发库重建，这不是本方案处理现有业务数据的授权；实施时不得以清库代替迁移。

### 15.2 推荐迁移步骤

1. 只读盘点现有图纸、project 字符串、附件、变更、版本及文件实际存在情况。
2. 生成项目归并候选，规范化空格等无业务含义差异；存在同名、同号或含义冲突时进入待整理清单，不自动强合并。
3. 老图导入时保留原图号、内部 ID、文件路径和全部历史版本；没有可靠项目归属的 Drawing 进入“待归属图纸”，不编造计划号或新图号。
4. 有整理权限的人员可把多个 Drawing 关联到项目，保留全部原 ID、编号别名和审计记录。同号冲突与项目归属通过映射页逐项核对，不根据型号、后缀或周表行号推断。
5. 挂接现有零件、BOM、附件、变更轮次。旧工单创建相应主事项包装，保留原编号和完整状态。
6. 现有技术状态、项目引用和发放事实分别映射。没有证明的历史内容标为“历史记录，正式状态待核对”；补录来源必须可见，不倒签审核或伪造发送回执。
7. 建立能够由历史证据支持的快照；缺失文件或依据显示缺项，不伪造补齐。
8. 核对总数、归属、内容指纹、历史版本、发布引用和权限；必要时冻结受影响记录写入，再完成切换。
9. 新旧路由兼容一段时间，集中写入一套新模型。不要长期让新旧系统独立双写相同业务。
10. 试点通过再扩大使用；回退方案包含数据库备份、映射和文件恢复路径。切换后新增业务需明确保留与回放办法，不能只降级前端导致记录丢失。

## 16. 分期交付与验收边界

时间成本受现有数据质量、部署条件和参与人员影响，本稿给出依赖与验收关口，不把未经评估的天数当作承诺。

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 0：规则与存量基线 | 名词、原图号规则、状态、权限、数据盘点、迁移样本、页面原型 | 用真实样例能唯一解释一个项目、多张老图和一次改图 |
| 1：项目与资料基础 | 项目、原图号关联、多图纸归集、资料分层、资料版本、统一上传与检索 | 老图原号不变；项目资料与图纸资料正确关联和隔离 |
| 2：变更与正式用图闭环 | 多目标变更、证据、轮次、技术审核、图纸发布包、发放回复、留存保护、基本时间线 | 一次配套改图从要求到技术完成可追溯，全部轮次和发放清单可还原 |
| 3：全过程与档案 | 生命周期树、固定历史回看、项目汇总、档案导出、完整性检查 | 任一正式版本能追到依据、批准、采用和原件；归档恢复校验通过 |
| 4：可选增强 | 高级对比、内容搜索／OCR、外部协同、技术流程模板 | 按实际业务价值逐项启用；生产系统联动若以后另有需求，再独立评估 |

阶段 1 解决整理问题，正式改图业务试点至少完成阶段 2 的审核、用图与留存关口。本次用户提出的全部目标需阶段 3 才算交付完整。阶段 1 起就保护业务引用版本并写入关键事件，不能等阶段 3 再补造历史。

不在首轮范围：完整采购财务、生产排程、全功能 MES、任意 BPMN 流程设计器、图数据库、AI 自动批准、任意 CAD 格式的精准几何理解。启动日期、加工安排、生产计划负责人和生产进度不作为 CAD 系统首期数据对象；如需联动，后续通过外部系统引用设计。

## 17. 验收用例

下列是实施验收标准，本次方案交付没有宣称这些功能已经通过测试。

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| A01 | 同一项目导入两套不同原图号及配套零件 | 都正常存在，图号、BOM、版本独立，项目汇总准确 |
| A02 | 一套老图被两个项目引用不同版 | 修改／发布源资产不自动改变任一项目的历史引用 |
| A03 | 单图项目 | 可直接进入图纸工作区，无强制计划层或空目录 |
| A04 | 项目资料被多张图纸作为依据 | 原件只管理一次，各处显示来源和采用版本 |
| A05 | 项目规范发布新版 | 旧审批保持原版，相关计划出现影响待办 |
| A06 | 项目要求与计划要求矛盾 | 产生待决冲突，系统不自动选择较新文件 |
| A07 | 同名文件再次上传 | 明确选择新版本或独立资料；旧内容可恢复查看 |
| A08 | 甲方口头提出修改 | 可快速记录并建任务，但不能自动标记书面批准 |
| A09 | 一次原因需要改两套图和工艺 | 一张主事项包含所有任务，依据与总体验证可追溯 |
| A10 | 审核退回后第二轮提交 | 两轮原件和意见都存在，批准准确关联第二轮 |
| A11 | 用户打开旧审核页面后内容变化 | 服务端拒绝过期批准，提示需重新核对 |
| A12 | 修改配套图纸只完成一套 | 默认不能发出完整图纸发布包，能指出缺项 |
| A13 | 本项目从 P01 更新到 P02 | 当前采用 P02，回看 P01 仍还原当时的图纸、依据与文件 |
| A14 | 两人同时发布同一项目的新组合 | 一次成功，另一次提示版本冲突；不能出现两份当前清单 |
| A15 | 导出包尚未发送，或下载后尚未回复 | 各自状态准确；导出不标已发送，下载不标甲方已确认 |
| A16 | 包发放后被撤销 | 旧包及回执保留，出现停用／更正记录，未来引用受控 |
| A17 | 普通变更未配置现场验证；另一变更明确要求专项验证 | 前者满足技术关口即可完成；后者须满足已设的验证要求，均不标生产完成 |
| A18 | 变更取消或退回后清理工作版本 | 被任何业务轮次引用的原件仍完整存在 |
| A19 | 两个项目同时改同一个共用零件 | 冲突按资产身份被发现，不能靠不同 drawing_id 绕过 |
| A20 | 发布按钮重复点击或请求重试 | 只产生一个正式包和一组应有任务 |
| A21 | 发布成功但通知服务暂时失败 | 包真实存在，待通知任务可重试，用户看到发送状态 |
| A22 | 上传中断／转换失败 | 已上传原件保留并可重试；错误预览不能进入必需正式成果 |
| A23 | 受限资料关联到普通项目 | 无权限者不能通过搜索、预览、导出或历史关系绕过限制 |
| A24 | 移动资料目录或更正原图号别名 | 历史链接、版本和批准依据不丢失 |
| A25 | 离职人员有历史批准及未完成任务 | 历史身份保留，任务交接有独立记录 |
| A26 | 计划归档后发现遗漏回执 | 添加补充记录和新档案版，不覆盖原归档内容 |
| A27 | 历史记录缺失实体文件 | 显示缺项，不虚构“完整归档” |
| A28 | 项目生命周期汇总跨计划变更 | 同源事件只计一次，可从相关计划进入 |
| A29 | 从备份恢复一个项目 | 数据库记录、实体文件、版本指纹和档案关系一致 |
| A30 | 导出旧图纸发布包后检查清单 | 文件内容、名称、版本、BOM 与当时批准一致 |
| A31 | 只导入原图号和文件 | 无需计划号、启动日期、加工安排、生产负责人、生产批次或生产明细，也可完成 CAD 归档和审核 |
| A32 | 导入重复图号和含字母的型号 | 保留原文并进入冲突核对，不把型号当图号，不把字母当修订，不按后缀编造项目 |
| A33 | 老图没有可靠项目归属 | 进入待归属，原图号与历史完整保留，不制造虚假的归属 |
| A34 | 项目没有正式包或某图纸引用被停用 | 明确显示尚未发布／停用，不回退到工作版或其他旧版 |
| A35 | 变更后点击管理员处理 | 管理员只能重派或记录异常，受影响图纸必须产生新轮次并由授权审核人完整审核 |
| A36 | 专利年费临近或有效期将至 | 按配置的提前节点提醒责任人，保存发送记录；未上传缴费凭证仍显示待处理 |
| A37 | 专利检测命中候选 | 显示来源、检测日期、匹配依据和待评估状态，不自动判定侵权或自动放行 |

易用性试点目标：经过简单培训，常见资料上传能在约 30 秒内完成归类；用户仅凭计划号能在约 10 秒内定位正式图纸。这是待验证目标，不是现有性能事实。观察任务完成率、误用率和操作步骤，不只看界面是否好看。

建议用一套专门的验收数据：1 个示例项目、2 个计划、2 套图纸、1 个共用零件、2 次甲方沟通、1 次跨图纸变更、2 轮提交、先后两版图纸发布包、1 份受限资料和 1 次归档补充，另加 1 张待归属历史图纸。用它贯穿开发、迁移演练和最终验收；演示关系不冒充周启动表中已证实的实际归属。

## 18. 当前采用的默认决策

为避免反复打断讨论，本方案已按以下默认决定形成一致设计：

1. 采用路线 B，沿用现有技术基础。
2. 项目和计划独立建模，计划可包含多个现有 Drawing 图纸组。
3. 界面保留目录体验；关键状态由业务动作决定。
4. 默认一个计划归一个项目，图纸资产通过采用关系复用。
5. 资料一个主归属、多处关联，正式引用固定版本。
6. 用户操作一张变更单，多任务拆分由系统承接。
7. 保留逐项修改说明、固定原件与技术检查；专项验证仅在实际要求时启用，高级自动比较作为辅助。
8. 区分技术审核、项目引用、文件发送和回复；这些都不代表生产实施完成。
9. 正式引用的所有版本与证据均受保护，包括退回轮次。
10. 全过程视图自动生成，按权限和重要程度展示。
11. 对外沟通首期支持原件登记与固定导出包，减少对外部账号集成的依赖。
12. 当前只完成方案；后续实施以增量迁移和真实用例闭环作为交付标准。

实施阶段需用真实台账收敛编号唯一范围、项目归属、图号映射、哪些技术事项必须甲方确认、实际审核授权和资料保留期限。默认采用保留原文、冲突待整理、正式技术成果独立复核、正式档案不自动删除的规则，不用猜测补齐业务事实。启动日期、加工安排和生产负责人不列为待确认需求。

## 19. 最终使用体验

用户打开项目，看到计划集合、项目资料和未结技术事项；打开计划，直接找到多套图纸、计划资料、变更和历史。技术员从生产反馈或甲方材料发起一张变更单，填写修改明细并上传成果；审核人看到准确的前后版本和证据。查图人员凭计划号获取正式图纸。任何有权限的人点开一个版本，都能看到为什么改、改了什么、依据是什么、谁修改和审核、发给了谁以及对方回复了什么。

## 20. V1.2 检查结论与本次修正

- 清除了首期生产批次、启动日期、加工安排、生产计划负责人和现场切换管理；保留 CAD 操作与审核的真实人员记录。
- 取消生产明细中间层，统一为项目 → 计划 → 多个图纸组，资料按项目／计划／图纸／变更分层。
- 修改闭环以技术成果、证据、审核和发布为核心；一般发放回执独立跟踪，专项验证按本次真实技术要求设置。
- 统一当前正式版、历史版、停用和多计划共用规则；文档、数据模型、验收用例与页面示意使用同一边界。
- 删除未经复核的表格汇总和编号推断，明确真实计划号与演示图纸映射的区别。

本次完成的是方案一致性检查与修正，可以作为后续实施的设计基线；没有据此宣称业务功能已经开发、部署或通过实施验收。
